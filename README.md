## 1. 为什么用 AlphaZero 而不是 PPO

你问的是"PPO 或者更好的其他 RL 算法"。对五子棋这类问题，AlphaZero 明显是更好的那一个，理由不是
"它更时髦"，而是几个具体的结构性原因：

**a) 奖励太稀疏，PPO 的信用分配很难。**
一局棋约 40 步，只有最后一步有 ±1 的奖励，中间 39 步没有任何信号。PPO 只能靠"整局赢了，所以
这局里每一步的 log-probability 都往上推一点"来学习，噪声极大。AlphaZero 给每一步都提供了一个
**密集的、逐步的监督信号**：那一步搜索出来的访问分布（策略目标）和搜索出来的胜率（价值目标）。

**b) 我们手里有完美的环境模型，不用搜索是巨大的浪费。**
五子棋是确定性、完全信息、零和博弈，规则就是一个完美的模拟器，可以任意前瞻、任意回退。PPO 是
无模型算法，它把这个模拟器当黑盒用；MCTS 直接用它做前瞻，同样的网络能力可以换来强得多的棋力。

**c) 最关键的一点：策略提升算子的强度完全不同。**
两个算法都是"策略迭代"的变体，区别在于怎么把当前策略变好一点：

- PPO 的提升方式是"沿着策略梯度走一小步"，受信任域限制，一步只能改进一点点。
- AlphaZero 的提升方式是"用 512 次前瞻搜索，算出一个比当前网络明显更强的策略"，然后让网络去
  **模仿这个更强的策略**（这就是 `learner.py` 里的交叉熵损失）。

搜索出来的策略比网络自己输出的策略强得多，所以每一局数据的信息量大得多。这就是 AlphaZero 样本
效率高出几个数量级的根本原因。同样地，价值网络学的是真实对局结果，价值变准 → 搜索变强 → 策略
目标变好 → 网络变强 → 价值更准，形成一个正反馈飞轮。

**d) 探索问题在 225 维离散动作空间上，PPO 很吃力。**
AlphaZero 用两个很干净的机制解决探索：根节点混入 Dirichlet 噪声，以及按访问次数采样落子
（见 `mcts.py` 的 `_add_dirichlet` 和 `sample_move`）。

**e) 经验证据。**
所有达到超人水平的棋类 AI（AlphaGo / AlphaZero / MuZero / KataGo / Leela）都是"网络 + 搜索"，
没有一个是纯 PPO。PPO 的主场是连续控制和 LLM 微调这类无法搜索、或者动作空间不适合搜索的问题。

一句话总结：**PPO 用梯度做策略提升，AlphaZero 用搜索做策略提升。在有完美模拟器的棋类问题上，
搜索是压倒性更强的提升算子。**

## 2. 系统全貌

```
                        ┌──────────────────────────────┐
   GPU 0                │  learner（train.py 主进程）   │
                        │  从回放池采样 → 一次梯度更新   │
                        │  每 500 步发布 latest.pt      │
                        └──────┬────────────────▲───────┘
                               │                │
                     latest.pt │                │ 下完的对局（mp.Queue）
                （权重，文件）  ▼                │
   GPU 1..7    ┌──────────┐ ┌──────────┐ ┌──────────┐
               │ worker 0 │ │ worker 1 │ │  ...  41 │   每个进程同时下 96 局
               │ 96 局并行 │ │ 96 局并行 │ │          │   每局 512 次 MCTS 模拟
               └──────────┘ └──────────┘ └──────────┘
```

两边**完全解耦**：worker 不等 learner，learner 不等 worker。唯一的耦合是
(a) 对局队列，(b) 权重文件。唯一被主动控制的是两者的**比例**——见下面的"数据复用率"。

一局自我对弈产生的数据长这样（`selfplay.py` 的 `GameRecord`）：

| 字段 | 含义 |
|---|---|
| `states` | 每一步的棋盘，**从当前该走棋一方的视角** |
| `policy` | 那一步 MCTS 根节点的访问次数分布（归一化）→ 策略目标 |
| `value` | 那一局最终结果，**从当前该走棋一方的视角** → 价值目标 |

## 3. 逐个文件讲解

建议按下面的顺序读。

### 3.1 `board.py` — 规则

棋盘就是一个 15×15 的 `int8` 数组，`+1` 黑、`-1` 白、`0` 空。全盘复制大约 1 微秒，这一点很重要：
它让 MCTS 可以在每次模拟开始时直接**复制根局面**，然后一路落子走下去，不需要实现"撤销落子"的
复杂簿记。

唯一不太显然的状态是 `near`：`near[r][c]` 记录以 (r,c) 为中心、半径 2 的方格内有多少颗棋子，
每次落子时增量更新一个 5×5 的切片。它的用途是 `candidate_mask()`：

```python
def candidate_mask(self):
    empty = self.stones == EMPTY
    mask = empty & (self.near > 0)
```

**只考虑距离已有棋子 2 格以内的空点。** 五子棋里离所有棋子都很远的一手永远没用，而这个剪枝把
分支因子从 225 降到 40 左右——同样的模拟次数，搜索能深得多。这是本项目最重要的单个优化之一。

判胜是 `_is_five`：从刚落的那颗子出发，沿 4 个轴向两边数同色连子。因为只在落子处判断，
所以是 O(1) 而不是全盘扫描。

### 3.2 `features.py` — 网络输入

5 个平面：我方棋子 / 对方棋子 / 对方上一手 / 我方上一手 / 我是不是黑棋。

两个设计点：

1. **一律用"当前该走棋一方"的视角**（`state = stones * to_play`）。这样网络不需要分别学习黑白
   两套镜像概念，参数利用率翻倍。
2. 第 5 个平面（常量，黑棋为 1）是必需的，因为五子棋**先手优势极大**，价值头必须知道自己站在
   这个不对称性的哪一边。

### 3.3 `network.py` — 网络与推理器

标准 AlphaZero 结构：卷积 stem → 10 个残差块（128 通道）→ 两个头。共 299 万参数。

两个头的设计值得说一下，因为它们各自解决一个具体问题：

**策略头**用两层 1×1 卷积压到 1 个通道，直接把每个格子的 logit 读出来（而不是接一个
7200→225 的全连接）。好处是**平移等变**：一个"活三"的形状不管出现在棋盘哪里，含义都一样，
这个先验对五子棋特别合适。而且参数少了 160 万。10 个残差块之后单格感受野已经覆盖全盘，
所以没有丢失全局信息。

**价值头先压到 1 个通道再接全连接**，让全连接层的输入是 225 维而不是 32×225=7200 维。
这一点不是美学问题，我一开始写的就是 7200 维的版本，结果**价值头在 100 步内就彻底死了**——
详见第 4 节。

`Evaluator` 是给 MCTS 用的批量推理器。里面有一个重要的性能技巧：**CUDA graph**。
这个网络很小但"层数很多"：一次前向有大约 70 个 CUDA kernel，每个 kernel 的 GPU 时间只有几微秒，
但 CPU 端启动它也要几微秒。在自我对弈的 batch 规模下，GPU 早就算完了、CPU 还在发射 kernel。
把整个前向录进一张 CUDA graph 后，每次推理只需要一次 launch 就能重放全部 70 个 kernel。

代价是 graph 只能重放它录制时的形状，所以推理**总是跑满 `graph_batch`，多余的行直接忽略**。
这是安全的，因为网络处于 eval 模式，BatchNorm 用的是保存下来的 running statistics，
输出的第 i 行只依赖输入的第 i 行。

### 3.4 `tactics.py` — 唯一的手写棋理

全项目只有这一处写入了人类棋理，而且只做一件极其明确的事：**精确判断"谁能一步成五"**。

实现方式是预先算好 `WINDOWS`：棋盘上所有长度为 5 的直线（15×15 一共 572 条）。然后：

```python
values = state[WINDOWS]        # (572, 5)
sums = values.sum(axis=1)
# sum == +4 <=> 我方 4 子 + 恰好 1 个空点
# sum == -4 <=> 对方 4 子 + 恰好 1 个空点
```

只要**一次求和**就能同时回答双方的问题。为什么成立：5 个值取自 {-1,0,+1}，和为 +4 只可能是
四个 +1 加一个 0（因为 a-b=4 且 a+b≤5 只有 a=4,b=0 这一解）。连成五会是 ±5，但那样棋局已经结束，
而这个函数只在活棋局面上调用。

在 MCTS 里它有两个作用（`interior_analysis`）：

- 我能一步成五 → 该节点价值**精确等于 +1**，不需要网络评估，直接当终局节点处理。
- 对方有唯一一个成五点 → 我**只能**下那一格（下别的都是下一手就输），候选着点直接缩到 1。
- 对方有两个不同的成五点 → 一颗子只能堵一个，该节点价值**精确等于 -1**。

为什么值得加这 126 行：纯网络 + 搜索在训练早期对威胁是"瞎"的。我的测试里，一个随机初始化的网络
面对"对方冲四"时，70 个候选着点每个只分到 5 次访问，根本发现不了"不堵就输"。加了它之后，这一整类
失误彻底消失，而代价只有几微秒。

注意它**只判断一步成五**，活三、双三、VCF 一概不管——那些留给网络自己学。

### 3.5 `mcts.py` — 核心

两个设计决定了这个文件的样子。

**(1) 为什么要跨对局批量化。** 一次 MCTS 模拟正好需要一次网络评估，而 batch=1 是最浪费 GPU 的
用法。所以我们不把一局搜完，而是**同时维持 96 局**，让它们的搜索齐步走：每一"轮"先把 96 棵树
各自走到一个叶子，把 96 个叶子**合成一个 batch 送进网络**，再各自展开、回传。搜索质量完全不受
影响（96 棵树彼此独立），GPU batch 从 1 变成 96。

**(2) 为什么用扁平 numpy 数组而不是节点对象。** 选择阶段要比较一个节点上所有候选着点的 PUCT 分数。
用"每个节点一行 numpy"（`N[node]`、`W[node]`、`P[node]`）时，这个比较是几个向量化操作；
用 Python 对象时它是一个 Python 循环，慢一个数量级。整棵树就是几个预分配的二维数组，
用 `[node, action]` 索引。

搜索本身是教科书式的 AlphaZero 三步：

```python
# select：从根一路取 PUCT 最大的边
scores = q + c_puct * sqrt(visits[node] + 1) * P[node] / (1 + N[node])

# expand：第一条还没有子节点的边变成新叶子，网络给出它的先验 P 和价值 v

# backup：把 v 加到路径上每条边，每上一层符号翻转
value = -leaf_value
for node, action in reversed(path):
    N[node, action] += 1
    W[node, action] += value
    value = -value
```

**符号翻转是最容易写错的地方**，所以值得说清楚：`leaf_value` 是"叶子节点该走棋那一方"的视角。
叶子的父节点是对手，所以它看到的是 `-leaf_value`；祖父节点又是同一方，看到 `+leaf_value`。

`sqrt(visits + 1)` 里的 `+1` 也不是随手写的：如果写成 `sqrt(visits)`，根节点第一次选择时
探索项整体为 0，`argmax` 会退化成"选第 0 号动作"，完全无视网络先验。

一个刻意的**简化**：每走一步都重建搜索树，没有复用上一手的子树。复用能省大约一半计算，但在扁平
数组表示下需要把子树重新索引/搬移，代码会明显变复杂。考虑到我们的瓶颈不在这里，我选择了可读性。

### 3.6 `selfplay.py` — 数据生成

每次 `step()` 让 96 局各走一步。落子方式是按访问次数采样（`sample_move`）：

- 前 12 手用温度 1.0（正比于访问次数）→ 开局多样性
- 之后用温度 0.25（正比于访问次数的 4 次方）→ 接近最优，但保留一点变化

温度不设成 0 是有意的：完全贪心会让自我对弈反复下同一盘棋。

### 3.7 `replay.py` — 回放池

预分配的环形缓冲，存最近 300 万个局面（约 30 分钟的自我对弈）。

用滑动窗口而不是保留全部历史，是因为网络在跟**自己**学：随着它变强，很老的数据只是"一个更弱的
自己当年怎么下"。滑动窗口让网络始终在拟合当前水平附近的数据，同时又平均了足够多的对局来保持稳定。

存储上做了一点压缩：局面存成 225 字节的 `int8`，而不是存展开后的 5 个 float 平面
（那样要 4.5 KB），平面在训练时才在 GPU 上现拼。

### 3.8 `learner.py` — 损失与更新

```
loss = 交叉熵(网络策略, 搜索访问分布) + MSE(网络价值, 对局结果)
```

两项各自在做什么，值得明确：

- **策略项**把搜索的成果蒸馏回网络。搜索比网络强（因为它前瞻了），这一项让网络去追上搜索。
- **价值项**让网络学会判断局面。价值变准，下一轮搜索就更准，策略目标也就更好。

这两项互相喂养就是整个飞轮。

唯一的额外技巧是**对称性增强**：五子棋在正方形的 8 个对称变换下不变，所以每个局面有 8 种等价
写法。实现上把一个 batch 切成 8 份，每份施加一种变换，全程向量化。注意策略目标要跟输入平面
**施加完全相同的变换**（所以先把 225 维策略 reshape 成 15×15 的"图像"再旋转）。

学习率有 1000 步的线性 warmup。这不是装饰：最容易把价值头推进 tanh 饱和区的正是最初那几十步。

### 3.9 `train.py` — 编排

一个 learner（主进程，GPU 0）+ 42 个自我对弈进程（GPU 1–7，每卡 6 个）。

最重要的一段是 `_may_train`，控制**数据复用率**：

```python
allowed = max_reuse_per_position * buffer.total_positions
return positions_consumed < allowed
```

`positions_consumed / positions_generated` 就是"平均每个局面被喂给网络几次"。我们把它压在 6 以内。
如果不管它，learner 会在少量新数据上反复空转，这是这类训练最经典的崩溃方式。实际效果是：
开局阶段 learner 大部分时间在等数据，后面才全速跑。日志里的 `reuse 6.00` 就是这个机制在生效。

另外有一个 `WorkerPool.respawn_dead`：6 小时无人看管的训练不应该因为某个 worker 撞上一次偶发
CUDA 错误就默默损失 1/3 的产能。

## 4. 踩过的四个坑（这部分其实最有信息量）

**坑 1：价值头在 100 步内死掉。**
最初价值头是 `32 通道 × 225 → 全连接`，即 7200 维输入直接接一个有界的 tanh 输出。
现象是 value loss 稳定在 **2.04** 不动。这个数字本身就是线索：目标是 ±1 时，
"预测饱和到 ±1 且与目标完全无关"的 MSE 恰好是 2.0。

打点确认：tanh 之前的激活值标准差在 100 步内从 0.115 冲到 **15.7**，tanh 彻底饱和、
梯度归零、再也回不来。原因是 AdamW 的步长与梯度大小无关，7200 个输入的权重同时朝一个方向
各走 lr 一步，输出就能被推出去很远。

修法是把价值头**先压到 1 个通道**（扇入 225），再加 1000 步 warmup。修好后
value loss 1.04 → 0.25，eval 模式下预测与真实结果的相关系数 +0.85。

**坑 2：差点误判成 BatchNorm 的 train/eval 不一致。**
排查坑 1 的路上，我先做的过拟合测试显示"train 模式 loss 0.167、但 eval 模式相关性只有 0.54"，
看起来像是 BatchNorm 的 running statistics 有问题（这是 AlphaZero 实现里很有名的坑，
因为自我对弈用 eval 模式、训练用 batch 统计）。

改用**每步新 batch** 重测之后，train / eval 的 loss 是 1.946 / 1.956，几乎一致——
前面那个 0.54 纯粹是"同一个 batch 重复 400 次"造成的假象。这个坑的教训是：
过拟合测试用来验证"能不能学"，不能用来判断"泛化行为"。

**坑 3：CUDA graph 在非 0 号卡上直接崩。**
`torch.cuda.Stream()` 和 `torch.cuda.graph` 用的是**当前设备**，默认是 `cuda:0`，
而张量在 `cuda:1`。一个设备上的 stream capture 不能往另一个设备派发工作，于是报
`operation not permitted when stream is capturing`。修法是把整个录制过程包在
`with torch.cuda.device(self.device)` 里。

**坑 4：网页版一改强度就整个卡死。**
MCTS 的树数组是按"构造时的模拟次数"预分配的，而网页服务只改了 `player.simulations` 这个计数器。
于是任何超过启动值（400）的档位都会写出数组边界，请求线程直接死掉，浏览器只看到连接被断开、
界面没有任何提示。

修了三处：`_ensure_capacity` 在每次搜索前按需重新分配（并加了回归测试
`test_simulation_count_can_change`）；`do_POST` 加上异常捕获并返回 500，而不是让线程静默死亡；
顺手修了 CSS——`body` 是 flex 容器且 `align-items` 默认 `stretch`，把 620×620 的 canvas
拉成了 620×760，棋子变成了椭圆。

**坑 5：对称性增强对固定 batch 完全失效。**
`_augment` 原本把"第 k 块用第 k 种对称变换"，也就是 batch 里第 i 个位置**总是**拿到同一种变换。
真实训练里每步都重新随机采样，所以长期看每个局面还是会见到全部 8 种变换，影响不大；
但它意味着对任何固定的 batch，增强是**完全无效**的——每个样本只会被以一种旋转呈现。

这个问题是写单元测试时暴露的：过拟合一个固定 batch 后 value loss 降到 0.051（拟合得很好），
但我在**未旋转**的原始局面上测相关系数只有 0.373。因为网络只见过每个样本的某一种旋转视图。
修法是每次调用随机一个变换偏移量（一行代码）。修完相关系数 0.958。

顺便：`baseline.py` 里我把候选着点**升序**排序了，于是 alpha-beta 一直在搜索自己最差的 8 手棋，
导致一个只训练了 4 分钟的网络能 12:0 血洗它。评估用的对手写错了，比模型写错更难发现，
因为它只会让你的结果好看。

## 5. 怎么运行

```bash
# 环境（已装好）
.venv/bin/python -c "import torch; print(torch.cuda.device_count())"

# 单元测试：规则、搜索、目标一致性
.venv/bin/python -m tests.test_core
.venv/bin/python -m tests.test_learning

# 战术题（6 道，全部由暴力枚举验证过答案）
.venv/bin/python -m tests.test_puzzles --checkpoint runs/az/latest.pt --sims 1600

# 训练
.venv/bin/python train.py --hours 6 --run-dir runs/az

# 评估：对传统 alpha-beta 引擎
.venv/bin/python arena.py --a runs/az/latest.pt --baseline-depth 3 --games 60
# 评估：两个 checkpoint 互搏
.venv/bin/python arena.py --a runs/az/latest.pt --b runs/az/step_0020000.pt --games 100

# 性能基准
.venv/bin/python bench_search.py --games 96 --sims 512
```

### 和它下棋

网页版（推荐）：

```bash
.venv/bin/python serve.py --checkpoint runs/az/latest.pt --port 8000
# 浏览器打开 http://localhost:8000
```

界面上可以选执黑/执白、选引擎强度（200 / 800 / 2000 / 4000 次模拟），
右侧实时显示引擎的胜率判断和它考虑过的几个候选点；还有"悔棋"和"求提示"。

终端版：

```bash
.venv/bin/python play.py --checkpoint runs/az/latest.pt --colour black --sims 800
# 输入坐标如 H8；可用命令 undo / hint / quit
```
